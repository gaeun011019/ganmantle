## 무엇이 달라졌나요?

명세 8절에서 1단계 게임과 2단계 랭킹 다음에 남아 있던 **3단계 채팅**을 구현했습니다. 이전 팝업은 열기·닫기만 가능했으며 실제 전송은 비활성화되어 있었습니다. 기존 파란 UI와 게임 규칙을 유지하고 전체 대화, 개인 대화, 초대를 수락해야 참여할 수 있는 단체방을 연결했습니다. 같은 `ganmantle-v1/`을 갱신했으며 별도 v2 폴더는 만들지 않았습니다.

기존 앱 서버 하나와 PostgreSQL을 그대로 사용합니다. 메시지는 HTTP 요청으로 저장하고, SSE 알림을 받으면 권한 검사를 거쳐 최신 기록을 조회합니다. 별도 채팅 서비스·Redis·런타임 의존성을 추가하지 않습니다. 서버 프로세스는 현재처럼 하나입니다.

## 어떤 코드인가요?

작성자는 요청 본문의 닉네임이 아닌 세션으로 결정합니다. 클라이언트 UUID는 재시도 식별자이며 DB 제약으로 같은 작성자의 같은 요청을 두 번 저장하지 않습니다.

```sql
UNIQUE (sender_id, client_id)
```

같은 ID를 다른 내용이나 방에 재사용하면 충돌로 거절합니다. 개인 대화는 정렬한 두 사용자 ID 조합을 유일하게 저장해 양쪽에서 동시에 시작해도 같은 대화를 사용합니다.

```sql
UNIQUE (direct_user_low, direct_user_high)
```

초대 수락 시에만 `chat_members`에 참여자 행을 만듭니다. `accessible_room()`은 메시지 읽기와 전송 모두에서 호출합니다. SSE에는 본문을 보내지 않고 `event: refresh`만 전달하며 본문은 권한 검사를 거쳐 다시 조회합니다. 갱신 신호는 DB 커밋 뒤에 보냅니다.

선택한 방과 방별 초안·전송 ID는 사용자별 키로 탭의 `sessionStorage`에 저장합니다. `setSaved()`는 전송 요청 전에 동기적으로 기록하여 응답이 끊기거나 즉시 새로고침해도 같은 ID로 재시도할 수 있게 합니다. 같은 탭의 새로고침과 팝업 닫기에는 복원되며 여러 탭의 초안은 서로 덮어쓰지 않습니다. 탭·브라우저 종료 시 초안은 사라질 수 있지만 전송된 메시지는 DB에서 복원됩니다.

메시지 ID로 중복을 합치고 이전 기록은 50개씩 읽습니다. `historyGeneration`과 커서 비교로 최신 페이지가 교체된 뒤 늦게 도착한 이전 조회를 버리고, 전송 후 다시 읽어 전송 이전 조회 결과가 화면을 되돌리지 않게 했습니다. SSE 연결 복구 시 빠진 기록을 조회하고, 연결 장애 중에는 15초 주기 조회도 사용합니다.

## 영향과 남은 일

- 적용 전 Windows 논리 백업 도구로 기존 DB의 custom 형식 백업을 생성했습니다. 백업은 제외 폴더인 `backups/`에 있습니다.
- 기존 `001_initial.sql`과 게임·정답·모델·점수 계산식은 변경하지 않았습니다. 신규 `002_chat.sql`은 시작 시 자동 적용되었습니다. 이전 앱 코드도 기존 게임 테이블을 사용할 수 있으며 되돌릴 때 채팅 테이블을 삭제할 필요는 없습니다.
- 메시지는 일반 텍스트로 DB에 보관합니다. 임의의 자동 삭제는 추가하지 않습니다. 공개 운영 전 보관·신고·삭제 정책을 정해야 합니다.
- 전체 어휘 유사도 순위와 기준 점수는 별도 미완료 기능입니다. 이번 작업에서 예시 점수를 넣지 않습니다.
- 다음 명세 단계는 4단계 배포 준비입니다. 실제 Mac·arm64 모델 실행과 실제 모바일 기기 검증은 남아 있습니다. GitHub 업로드와 공개 배포는 하지 않았습니다.
